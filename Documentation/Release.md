# Release and publication

The first release candidate is package version `1.0.0` with matching tag `1.0.0`. CI and nightly run the complete Node 24 validation on self-hosted macOS. Tag creation, GitHub release publication and npm publication are separate owner-authorized actions.

The `npm-publish` GitHub environment is configured with a required owner reviewer and protected-branch deployment policy. The publish workflow must be dispatched from `main` with one exact published GitHub release tag. An unprivileged preflight validates the tag syntax, resolves the tag through the GitHub API, requires its commit to equal the protected `main` dispatch SHA, and confirms a non-draft release exists. The environment-protected OIDC job consumes only that preflight commit SHA, installs from the lockfile, runs the complete package validation, and requires exact `package.json`/tag equality. Only then does it publish through npm trusted publishing. Release and input context enter shell steps through environment variables rather than expression interpolation. The protected job has only `contents: read` and `id-token: write` permissions and stores no npm or App Store Connect token.

Npm requires the package to exist before a trusted publisher can be configured. The initial `1.0.0` registry creation therefore uses a one-time owner-authenticated npm CLI session from the exact clean `1.0.0` tag checkout. After separate authorization, the owner runs `npm ci`, `npm run check`, inspects `npm pack --json --dry-run`, signs in with the npm account and its required second factor, and runs `npm publish --access public`. The owner then logs out or removes the bootstrap credential immediately. Once the package exists, configure npm trusted publishing for `thatfactory/app-store-connect-mcp`, workflow file `publish.yml`, and environment `npm-publish`, and explicitly enable the trusted publisher's direct `npm publish` permission. All later npm releases use the protected workflow; do not retain an npm token in GitHub.

For later releases, the owner first creates the exact tag and publishes its GitHub release. Npm publication still does not start automatically. The owner separately dispatches `Publish to npm` from `main`, enters the published tag, and approves the `npm-publish` environment deployment. The concurrency key prevents simultaneous runs for the same tag, while npm remains authoritative against publishing the same version twice.

Before any publication, verify the release checkout is clean, run `npm ci && npm run check`, and inspect `npm pack --json --dry-run`. The allowlist permits only `dist/`, `resources/`, `package.json`, `README.md`, and `LICENSE`. The package smoke test installs the tarball with production dependencies in a fresh external directory, checks the executable bit, help/version output, MCP tool/resource discovery, and offline validation. Repository examples, tests, contracts, source maps, local plans, app identifiers, contacts, credentials, and signing artifacts are excluded.

Known evidence limits remain part of the release record. Discovery, export, multi-locale text synchronization, and commerce readback have live evidence. Screenshot synchronization has synthetic coverage. Signing lifecycle and review submission use mocked Apple responses. Review readiness cannot guarantee Apple acceptance, generic availability mutation remains manual, and initial App Store app creation remains a website bootstrap.

Creating the tag, publishing the GitHub release, performing the one-time initial npm publication, configuring the trusted publisher, or approving a later protected npm deployment each requires separate owner authorization.
