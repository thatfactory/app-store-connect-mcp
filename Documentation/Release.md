# Release and publication

The first published version is `0.1.0` with matching GitHub tag `0.1.0`. Its one-time owner-authenticated npm bootstrap is complete. CI and nightly run the complete Node 24 validation on self-hosted macOS.

For subsequent versions, merge the reviewed version change to `main`, create its matching tag, and publish the GitHub release. The `release: published` event automatically starts `Publish to npm`; no manual workflow dispatch or environment approval is required. Publishing a GitHub release is the authorization to publish that version to npm. The tag must exactly match `package.json` (for example, `0.1.1`, without a `v` prefix).

An unprivileged preflight validates the tag syntax, resolves lightweight or annotated tags to a commit, requires a release-event tag to still match the event commit, verifies that commit belongs to `main` history, and confirms a non-draft GitHub release exists. The publish job checks out only that immutable commit, installs from the lockfile, runs the complete package validation, and requires exact package/tag equality before publishing. Advancing `main` after tagging does not change the source being published. The per-tag concurrency group queues concurrent runs rather than interrupting an in-flight publication; npm rejects any attempt to publish an existing version again.

The `npm-publish` GitHub environment remains part of the npm trusted-publisher identity. It has no required reviewers or wait timer and permits release tags plus the `main` branch used for manual recovery. Configure its selected deployment policies as branch `main` and tag `*`. Keep npm trusted publishing configured for `thatfactory/app-store-connect-mcp`, workflow `publish.yml`, environment `npm-publish`, with direct `npm publish` permission enabled. The publish job has `contents: read` and `id-token: write`; no npm or App Store Connect token is stored in GitHub. Release/input context enters shell steps through environment variables.

A manual recovery path remains: dispatch `Publish to npm` from `main` with an exact already-published GitHub release tag whose npm version has not yet been published. It performs the same immutable-source and package checks. Do not dispatch `0.1.0`, which already exists on npm. Adding this workflow does not retroactively republish old releases.

Before any publication, verify the release checkout is clean, run `npm ci && npm run check`, and inspect `npm pack --json --dry-run`. The allowlist permits only `dist/`, `resources/`, `package.json`, `README.md`, and `LICENSE`. The package smoke test installs the tarball with production dependencies in a fresh external directory, checks the executable bit, help/version output, MCP tool/resource discovery, and offline validation. Repository examples, tests, contracts, source maps, local plans, app identifiers, contacts, credentials, and signing artifacts are excluded.

Known evidence limits remain part of the release record. Discovery, export, multi-locale text synchronization, and commerce readback have live evidence. Screenshot synchronization also has live macOS evidence: ten original JPEGs across five locales reached COMPLETE with matching MD5 values and exact ordering; final reconciliation returned noOp. Recovery retained a verified upload and removed only explicitly planned abandoned or stalled reservations. Signing lifecycle and review submission use mocked Apple responses. Review readiness cannot guarantee Apple acceptance, generic availability mutation remains manual, and initial App Store app creation remains a website bootstrap.

Creating and publishing a new GitHub release requires owner authorization and now also authorizes the corresponding automatic npm publication. Trusted-publisher configuration changes remain separately authorized.
