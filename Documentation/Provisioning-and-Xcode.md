# Bundle IDs and static Xcode proposals

`inspect_xcode_project` reads one explicit project, app or app-extension target, configuration and platform within an approved checkout. An optional workspace is checked for direct project membership; nested groups or unresolved membership remain provisional. It uses Apple's `/usr/bin/plutil` with a fixed argument vector, bounded input/output and a five-second timeout to decode project and entitlement plists. It never runs xcodebuild, builds, resolves packages, evaluates scripts or edits project files. Non-macOS hosts report inspection unavailable without preventing server startup or other tools.

Simple project/target build settings and variable substitutions are resolved with source hashes and provenance. Conditional settings, external xcconfig references, missing variables and cycles remain explicit gaps. Their values must be resolved manually before relying on a bundle-ID proposal. SDKROOT `auto` is checked against static supported platforms. Tests and frameworks cannot be selected as apps; extensions require their own explicit selection. Development team and API issuer are different identities.

Capability mapping version 1 proposes Push Notifications, Associated Domains, Game Center, Sign in with Apple, App Groups, iCloud and Apple Pay from known entitlement keys. It distinguishes setup-dependent proposals and known sandbox-only permissions. Unknown keys remain unresolved. This mapping is a proposal, not evidence that a capability is enabled or fully configured in the portal. Source: [Apple's capability setup guide](https://developer.apple.com/help/account/identifiers/enable-app-capabilities/).

## Explicit provisioning plans

`get_bundle_id_state` discovers the exact portal platform and capabilities before configuration is authored. `plan_provisioning_changes` requires an AppStore root and exact identifiers declared in provisioning.json. Its read-only Apple discovery matches identifiers exactly, checks requested portal platforms and rejects ambiguity. `IOS`, `MAC_OS` and `UNIVERSAL` are portal enum values, not Xcode SDK names. A primary identifier must cover the app.json platforms. Additional identifiers are never included implicitly.

Absent identifiers produce create operations; existing identifier IDs/names are preserved. Capabilities absent from the request remain unmanaged, including when the list is empty. New capabilities depend on verified registration. Apple-initialized capabilities are recognized by readback instead of duplicated. All writes use the shared approved plan engine, never an inspection shortcut.

The bounded v1 adapter enables Game Center, Push Notifications, Associated Domains and In-App Purchase, and creates/updates Data Protection on explicitly IOS identifiers. Data Protection requires all three documented protection options with exactly one selected, using the pinned `DATA_PROTECTION_PERMISSION_LEVEL` setting. Other capability settings, group/container/merchant associations and signing-service setup report `capabilitySetupRequired`. Capability removal is not inferred or exposed. Unrecognized settings fail closed rather than being discarded. Supported platform references: [iOS](https://developer.apple.com/help/account/reference/supported-capabilities-ios/) and [macOS](https://developer.apple.com/help/account/reference/supported-capabilities-macos/), checked 2026-09-06.

Capability modifications can invalidate provisioning profiles across eligible platforms. APNs capability registration alone does not create APNs credentials or finish TLS-certificate setup. These impacts appear with the plan; the adapter never revokes or regenerates signing assets. App-record creation remains a separate manual bootstrap. The API request shapes are pinned in contracts/apple-openapi.json; these boundaries are narrower than its full capability enum.

## Acceptance

Sixteen mocked/static tests cover exact IDs, absent/existing registrations, platform checks, omitted capabilities, dependency order, explicit settings updates, permissions/conflicts, uncertain create reconciliation without replay, repeated no-op, app/extension/test selection, substitutions, unknown entitlements, sandbox separation and no source mutation. Native plutil is also tested on macOS.

Read-only verification covered exact bundle discovery and a zero-operation capability plan. Capability resource IDs use Apple's underscore-delimited form; the identifier validator and receipt tests cover that format. Static Release-configuration inspection reports conditional build settings as unresolved rather than evaluating the project. These checks do not claim live acceptance of signing mutations.
