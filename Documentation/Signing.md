# Explicit signing resources

Signing support is a bounded lifecycle tool, not a signing-key manager. `get_provisioning_resources` reads certificates, registered devices and profiles without returning certificate/profile contents, raw serial numbers, UDIDs or profile UUIDs. It returns exact App Store Connect resource IDs for later selection and SHA-256 fingerprints for sensitive identifiers. Results are bounded and can be filtered by family and up to 100 exact IDs.

`plan_signing_changes` accepts exactly one typed action: create or revoke a certificate, register or update a device, or create or delete a profile. Every operation is sensitive in the public plan and requires ordinary exact plan approval. Revocation and profile deletion are separate destructive operations. Certificate revocation reports affected profile count and never revokes another certificate or creates a replacement. Capability plans never regenerate profiles.

Certificate creation accepts one contained PEM PKCS#10 CSR under the approved root. The packaged code invokes the native `/usr/bin/openssl` tool with a ten-second/64 KiB output bound, verifies the request signature, and accepts supported RSA or named EC public keys. It rejects private-key PEM blocks and never generates, imports, exports or reads a private signing key. The App Store Connect API key remains independent from app signing identities. Active certificates of the selected type are counted in the plan; Apple remains authoritative for account-specific quotas, and no certificate is revoked to evade a limit.

Device registration uses one explicit name, platform and UDID. Updates select one exact device and only a supplied name and/or status. A conflicting existing UDID stops planning. Profiles select one exact bundle ID, a nonempty explicit certificate list, and only the device IDs named by the caller. The planner checks the bundle platform, certificate type/platform/activation/expiration, device status/platform, and distribution-type device rules. It never attaches all visible devices or chooses a certificate. Existing profile names stop implicit replacement.

Create uncertainty is reconciled from the complete before/after inventory and exactly one new resource with the approved attributes and relationships. Update, revocation and deletion postconditions preserve unrelated inventory. A certificate revocation may transition its affected profiles to `INVALID`; that declared effect is accepted only for profiles that referenced the exact revoked certificate. Any other concurrent inventory change leaves the operation unverified. Writes are never replayed.

`download_signing_artifact` fetches one exact certificate or profile, validates its binary envelope, and writes only to a new absolute path whose parent is within an approved root. It uses exclusive, no-follow creation with mode `0600`, flushes the file, and returns only path, type, size and SHA-256. Existing paths are not overwritten. Artifact bytes, CSR contents and CSR subject data do not appear in MCP responses or tracked examples; the plan reports only the verified public-key algorithm and size/curve. Nothing is committed automatically.

Automated coverage uses temporary development resources and mocked Apple responses. It exercises CSR parsing/private-key rejection, weak keys, exact selection, expiration, platform/type compatibility, device conflicts, role denial, uncertain creates, explicit destructive effects, inventory redaction and secure downloads. No live certificate, device or profile is created, revoked or deleted, and Headroom's working signing setup is not modified.
